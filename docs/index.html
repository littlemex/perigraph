A record of what surrounded the model, and of what answered.

One record per model call. Every part of the harness and of the model is identified by a digest of its exact content, says how that fact reached the record, and, when it is missing, says whose fault the gap is. A receiver can then refuse a claim about accuracy or cost that the records cannot support.

The problem

The names stayed the same. The answers did not.

A comparison between two runs is only as good as the evidence that each side was what its name says. In one distillation study, each of these changed the answers while every name stayed the same.

Sources: tierbook verification record (rows 1 to 4) · Prismyra commit 84cf43d (row 5)

Two failure directions. The first four made two different things look the same; the fifth made the same thing look different. A content digest catches the first kind, and it catches the second only when it covers what the model actually reads and nothing else. Most of the specification is about that second condition.
How it is designed, and why

Nine decisions, each with the failure it prevents

Each decision is stated with the alternatives that were weighed. Open one to see them. The section of the specification that makes it normative is named on each card.

1 · SPEC 2.2

A digest of each part's content, not its name

A prompt can stay v3 while its text changes, and a model name can survive a re-training. Each part carries the sha256 of its exact content; names are labels for a reader.

Alternatives weighed
A name and version per component, which every convention surveyed carries and which the incidents above defeat. One digest over the whole prompt, which says that something changed but not which part.
2 · SPEC 2.1, 2.4

Every digest names its boundary

A tools array is in the request, but the provider renders it into the prompt however it likes. Only a model_visible digest keys the harness identity, and that text is hashed raw. For a Chat Completions request, the identity is the instruction's alone, and the record says so.

Alternatives weighed
Keying on every field, which changes when a gateway re-serialises JSON and stays the same when a provider changes how it renders tools. Canonical JSON everywhere, which makes two instructions that differ only in white space look identical, though such differences change model behaviour.
3 · SPEC 1.1a

Every fact says how it reached the record

Five sourcing values, per part. A pulled fact carries how many seconds before the request it was read. A claim nobody downstream can check may trigger a refusal and may never lift one.

Alternatives weighed
Trusting declared metadata, which lets a statement stand in for an observation. Refusing declarations outright, which throws away the only source for parts a request cannot carry, such as a retry policy.
4 · SPEC 1.2, 1.3

Every absence names whose fault it is

A collector that loses the ability to read a field after a client library renames it would otherwise write the same gap as a requester who sent nothing. Each absence blames the requester, the collector or nobody, and the collector publishes in advance what it can reach.

Alternatives weighed
Omitted or null fields, which cannot tell a regression from an empty request. A free-text reason, which no receiver can act on.
5 · SPEC 1.1

Permissive toward the sender, exact about itself

A record missing any number of parts is still a record, because a refused record looks the same as a run that never happened. Every failure path, an exception included, still emits one, with status collector_failed.

Alternatives weighed
Strict validation that rejects incomplete records, which turns every partial observation into silence.
6 · SPEC 9

What answered is identified by the process that loaded it

Checkpoint files, precision after loading, runtime packages and answer mode: one part for each incident above. Only loaded_by_us keys the model identity. A model behind a provider's API has none and stays admissible.

Alternatives weighed
A model name or a provider's model identifier, which is a label. A digest of the stored files alone, which cannot tell bf16 from int8 of the same files.
7 · SPEC 10

A model's history is a separate document that can only subtract

Its trainer writes the parent, the method and the item sets used, about one artifact identity. A set named as trained on makes a verdict on that set suspect. A missing ancestor is unknown, never clean.

Alternatives weighed
Lineage fields in every record, which would make the server that holds the bytes vouch for a history it does not hold.
8 · SPEC 6

Flat attributes, keyed by part name

The record rides on a span any tracer already emits, on a log line or in a file. Keys never use positions, which shift when a collector learns one more part. A missing identity is omitted, never an empty string that would group every unidentifiable run.

Alternatives weighed
A nested JSON document, which needs a serialiser on both ends and puts the record's shape into the transport, where every change to it breaks compatibility.
9 · SPEC 8

Conformance is a closed list of refusals

A receiver conforms by refusing what records cannot support, and by not refusing what they can, such as a record missing parts. So a receiver cannot become conformant by refusing everything.

Alternatives weighed
A list of capabilities a receiver supports, which says what it can do and not what it will not let through.
Refusals

The collector never refuses. The receiver does.

A collector that dropped a partial record would leave a hole nobody can see, so it always emits one and names what it could not read. All the refusing happens at the receiver, against a closed list.

Thirteen refusals a receiver performs

Each exists because a published number would otherwise have had to be withdrawn. They are listed as receiver_obligations.must_refuse in spec/vocabularies.json.

Four it must not

A record missing parts, an incomplete record kept as a log, a record with no model identity, and one with no model half at all. Refusing these would make a receiver conformant by refusing everything.

Relation to existing conventions

It rides on a span. It does not replace one.

The other attributes of a span say what was said. A perigraph record on the same span says whether two runs were the same. None of the three conventions surveyed carries a content digest per part or a sourcing mode per part.

Quickstart

Three languages, one identity

No package is on a registry yet, so each quickstart runs from a clone. All three record the same request and print the harness identity c8f8edc45e222f663d8d70ac.

git clone https://github.com/littlemex/perigraph.git
cd perigraph
python3 -m venv .venv
. .venv/bin/activate
pip install .
python examples/quickstart.py
git clone https://github.com/littlemex/perigraph.git
cd perigraph/typescript
npm install
npm run build
node examples/quickstart.mjs
git clone https://github.com/littlemex/perigraph.git
cd perigraph/go
go run ./examples/quickstart

Python and TypeScript end with harness identity: c8f8edc45e222f663d8d70ac and verdict: admissible, after reading the record back as a receiver. Go is a sender only and ends with the identity.

Conformance, for any language

The runner checks an implementation through a small adapter that reads one JSON request per line and answers one line each. It never imports the implementation. Collectors are checked against the identity fixtures and the record schema, stampers against the model fixtures, and receivers against the receiver cases.

pip install jsonschema
python tools/conform.py --adapter "python conformance/adapters/python_adapter.py"

Status

Version 2, provisional

spec_version is a single integer. Removing or renaming a value, changing what one means or how an identity is computed, and adding a receiver refusal are breaking. A change that only withdraws an identity is not, while every known sender is built from this repository. A formal versioning and compatibility policy is planned and not yet in place.

What it does not cover

  • Whether a claim is true, or which model should answer.
  • Authenticity: records are not signed, and a receiver trusts the collector for every digest it did not compute.
  • Secrecy: a digest of short or predictable content can be recovered by guessing.
  • How a provider renders tools and settings into the prompt.
  • Run-to-run nondeterminism, such as batch-dependent kernels.
  • Portable checks of the comparison refusals, which need facts the version 2 record does not carry.

Roadmap, without dates

  • A formal versioning and compatibility policy.
  • Signed records, stamps and lineage documents, and keyed digests.
  • A carrier for a model stamp between the serving process and a router, with attribution.
  • Attributes for the facts the comparison refusals read, and conformance cases for them.
  • Bindings for more request shapes, and the Chat Completions fields not read today.
  • Published packages, more maintainers, and an independent implementation.
