# Ambiguities and readings

## Clarified by the current specification

- **System messages:** Only string `content` in system-role messages supplies `instruction`. Multiple strings are joined with one U+000A in message order. An instruction empty after trimming the specified Unicode `White_Space` property is `not_provided`; otherwise its digest uses the untrimmed, joined text. Any non-string or missing system content fails the entire instruction extraction, with its message index and JSON type in the detail; content is never quoted.
- **Request templates:** A missing, null, or verified whitespace-only `perigraph_template` is `not_provided`. Every declared entry is checked against its corresponding message before the emptiness test. A contradiction is `extraction_failed` and withdraws the harness identity even when `instruction` is held. A held template refines an identity established by an instruction but never establishes one alone, even beside `generation_controls`. Lengths in its framed digest are UTF-8 byte counts.
- **Empty request values:** An empty `tools` array is `not_provided`. There is no emptiness rule for members digested at `canonical_value`: even an empty `response_format` object supplies `generation_controls`, while independently supplied sampler settings supply `decoding`. A null top-level member supplies neither part.
- **Malformed request fields:** A non-object body fails extraction for every part in the static manifest. A wrongly typed `messages` array or entry fails the parts read from messages; it does not fail `tool_trace`, which this binding does not read from messages. A wrongly typed `tools` array, entry, or present `function` object fails `tool_schemas`, without affecting parts read elsewhere. A `response_format` of any JSON type is read at `canonical_value` into `generation_controls`, without an object type check. Such input does not by itself make the collector’s terminal status `collector_failed`.
- **Manifest and wire form:** Manifest order has no meaning; an empty manifest is the empty string. A request-only collector writes four `not_observable` model absences and omits both model identities. All three identity attributes are omitted when absent. For a JSON object it also writes the unlisted-member names and omitted count, including an empty set and zero count; for a non-object it writes neither.
- **Precision:** An empty value, or `auto` as any value or as a dtype name, is unresolved. The `auto` comparison trims the Unicode `White_Space` property specified in section 1.2 and ignores ASCII case. Accepted values are digested as read, without trimming. `PrecisionDigest` returns an error for an unresolved value; a collector recording the failed observation reports `precision` as `extraction_failed`.

## Remaining interpretations and limitations

- `FromRequestJSON` can detect an unpaired surrogate escape while the JSON text is available. Go’s `encoding/json` replaces one with U+FFFD before `FromRequest` or `FromRequestValue` can see it; callers using those decoded-value APIs must not present a substituted value as the original JSON text.
- A nonempty `tools` array is held at a collector-local `parsed` boundary. The request does not provide the exact rendering of tool schemas shown to the model, so this digest cannot identify a harness.
- Assistant `tool_calls` or `function_call` and tool-role messages already present in the request do not supply a trace under this binding. `tool_trace` is `not_provided`; no future calls are inferred.
- `response_format` is read only into `generation_controls`, not `readout` or `decoding`. `readout` is the owner's rule and is `not_provided` without a declaration. Listed sampler and score-reporting members supply `decoding`. Each canonical part digests an object of its present, non-null members using the normative `canonical_value` serialisation; its label contains sorted member names only. A `parsed` digest remains collector-local.
- Absent `loop`, `turn_budget`, `retry_policy`, `readout`, and `context_partitioning` are `not_provided`; `tool_extension` is structurally `not_observable`. This adapter’s manifest is always `instruction,request_template,tool_schemas,generation_controls,decoding`.
- The binding's closed member list records `seed` and other listed transport or accounting members nowhere. Other top-level names are reported, never valued, in `perigraph.request.unlisted` or its omitted count; neither attribute keys an identity. An unlisted member's unrepresentable value cannot fail a canonical part.
- `generation_controls` is `in_the_request` at `canonical_value` and refines an instruction identity; by itself, or beside only a request template, it establishes none. A required identity part held with other sourcing or at another boundary does not satisfy `must_be_known_for_identity`.
- Checkpoint paths are ordered by their UTF-8 bytes. The digest API receives paths and file digests, not an artifact root; the caller must resolve symlinks, hash file bytes, and enumerate every file the process read before invoking it.
- Precision lines are sorted by complete field name; runtime lines by distribution name. Nonempty serializations end in a newline. This API cannot itself verify that precision was read from loaded parameters or that a runtime package list is static per collector version.
- `Loaded` must be called during the load, in the process that loaded the model. Replacing a request record’s default model half with its result attaches that in-process stamp.

## New ambiguity

- Section 1.2 still assigns shared failures to malformed `messages` entries, while this binding reads only `instruction` and `request_template` from messages. A malformed nested field used by neither, such as an assistant `tool_calls` value of the wrong type, therefore does not by itself fail `instruction` or create a `tool_trace` part.
